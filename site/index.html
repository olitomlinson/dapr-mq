Get Started

Quick Start: k8s install

Install daprMQ, then check it works with a simple smoke test. Everything is a pre-release until 1.0.

Installs Dapr, Postgres, a state store Component and daprMQ, in that order.

Dapr, Postgres and daprMQ
echo "▶ [1/4] Installing Dapr 1.18 (1–2 min)…"; S=$SECONDS
helm repo add dapr https://dapr.github.io/helm-charts/ >/dev/null
helm install dapr dapr/dapr --version 1.18.7 -n dapr-system --create-namespace --wait >/dev/null \
  && echo "✅ Dapr ready ($((SECONDS - S))s)" || echo "❌ Dapr failed to install, see the error above"

echo "▶ [2/4] Installing Postgres (1–2 min)…"; S=$SECONDS
helm repo add bitnami https://charts.bitnami.com/bitnami >/dev/null
helm install postgres bitnami/postgresql -n daprmq --create-namespace \
  --set auth.postgresPassword=daprmq_secret_123 \
  --set auth.database=actor_state --wait >/dev/null \
  && echo "✅ Postgres ready ($((SECONDS - S))s)" || echo "❌ Postgres failed to install, see the error above"

echo "▶ [3/4] Creating the Dapr state store component…"
kubectl apply -n daprmq -f - >/dev/null <<EOF \
  && echo "✅ State store created" || echo "❌ State store failed, see the error above"
apiVersion: dapr.io/v1alpha1
kind: Component
metadata:
  name: statestore
spec:
  type: state.postgresql
  version: v2
  initTimeout: 60s
  metadata:
    - name: connectionString
      value: "host=postgres-postgresql.daprmq.svc.cluster.local user=postgres password=daprmq_secret_123 port=5432 database=actor_state"
    - name: actorStateStore
      value: "true"
EOF

echo "▶ [4/4] Installing daprMQ (1–2 min)…"; S=$SECONDS
helm install daprmq oci://ghcr.io/olitomlinson/charts/daprmq \
  --devel --wait -n daprmq \
  --set dapr.stateStoreName=statestore >/dev/null \
  && echo "✅ daprMQ ready ($((SECONDS - S))s)" && echo "✅ All done. Run the smoke test below." \
  || echo "❌ daprMQ failed to install, see the error above"

  echo "❌ Couldn't read the state store component, see the error above"
elif [ -z "$SCOPES" ]; then
  echo "✅ The state store has no scopes, so daprMQ already has access"
elif echo "$SCOPES" | grep -q '"daprmq-daprmq-worker"'; then
  echo "✅ daprMQ is already in the state store's scopes"
else
  kubectl patch component {your-dapr-state-store-name} -n daprmq --type json \
    -p '[{"op":"add","path":"/scopes/-","value":"daprmq-daprmq-worker"}]' >/dev/null \
    && echo "✅ Added daprmq-daprmq-worker to the state store's scopes"
fi
Install DaprMQ with helm

  --devel --wait -n daprmq \

  && echo "✅ daprMQ is now installed. Run the smoke test below." \

Smoke test
kubectl port-forward -n daprmq svc/daprmq-gateway 8080:8080 >/dev/null &
sleep 2

echo "Enqueue:"
curl -s -X POST localhost:8080/queue/hello/enqueue -w '\n' \
  -H 'Content-Type: application/json' \
  -d '{"items":[{"item":{"hello":"daprMQ"}}]}'

echo "Dequeue:"
RESPONSE=$(curl -s -X POST localhost:8080/queue/hello/dequeue -H 'require-ack: false')
echo "$RESPONSE"

echo "$RESPONSE" | grep -q '"hello":"daprMQ"' \
  && echo "✅ Smoke test passed: the message went in and came back out" \
  || echo "❌ Smoke test failed: the message did not come back"

kill %1

Features

Everything a modern transactional queue needs.

Just enqueue and dequeue is all you need to get started! Every other feature is optional, and layers on cleanly when you need it.

⇄

It Just Works

Enqueue and Dequeue are all you need to get going. Queues are created on demand, with no provisioning step.

There is no create-queue call. The first Enqueue or Dequeue against a queue name brings it into existence, and a queue nobody uses costs nothing. Send any JSON payload and get it back exactly as you sent it. Everything else on this page is opt-in, one header or field at a time.

HTTP and gRPC API Surface

Call daprMQ over simple HTTP or gRPC interfaces

Every operation is available over plain REST (JSON over HTTP/1.1) and over gRPC (HTTP/2), served by the same gateway. gRPC adds two streams, Consume and ConsumeSession, that push messages to you instead of you polling for them.

Client SDKs

Typed clients for .NET, Java, Go, Python and TypeScript.

All five SDKs share one proto contract, so behaviour is the same in every language. Each wraps the full API over HTTP or gRPC, with managed consumers for plain queues and sessions that handle locks, acknowledgements and nacks for you. None of them depend on Dapr.

See the SDKs →
📜

Guaranteed FIFO

Strict first-in-first-out ordering per queue — no reordering, no surprises, no partitions to reason about.

Each queue is a single Dapr actor that handles one call at a time, so messages come out in exactly the order they went in. Every message is stamped with a sequence number, so even a message whose lock lapses or that is nacked goes back to the position it was taken from rather than the back of the queue.

Concurrency model →
⚡

Priority Support

Route urgent messages ahead of normal ones. Unbounded priority levels, 0 = highest.

Set priority per message: 0 is the fast lane, and the default is 1. Dequeue drains lower numbers first and stays FIFO within each priority. Each priority level is its own sub-queue, so there is no fixed number of levels to configure.

Enqueue reference →
✓

Acknowledgements

Optional at-least-once delivery — Ack, Nack, Extend Lock, or Ack up to 1000 at once. An unacknowledged message goes back to the position it was taken from, not the tail.

Dequeue with require-ack: true and the message is locked rather than removed, for a TTL you choose (1–300 seconds). Then Acknowledge to finish it, Nack to hand it straight back, or Extend Lock to keep working. Acknowledge Batch settles up to 1,000 locks in one call. A lock that lapses returns its message to its original position, and every redelivery counts toward the max delivery count.

Acknowledge reference →
📡

Pub Sub

Publish messages to a Topic, automatic fan-out to many independent Subscriber Queues.

Publish once to a Topic and daprMQ copies the message to every subscriber's own queue. Each subscriber gets the full queue feature set (FIFO, locks, dead-lettering), and can register an HTTP Sink in the same call to have messages pushed to it. Topics are created on demand, like queues.

Topics reference →
📊

Session / Message Group

Messages within a Queue can be assigned a Session ID. Consumers can lease one or more Sessions and receive a FIFO stream of messages

Tag messages with a sessionId and they are grouped within the queue. A consumer accepts a session (any free one, or a specific one) and holds an exclusive, renewable lease on it, so different sessions are processed in parallel while each stays in strict order. Every SDK has a SessionQueueConsumer that runs a pool of sessions for you.

Sessions reference →
🔑

Message Deduplication

Attach a client-supplied Idempotency key to a message — duplicate submissions within a configurable TTL window are silently dropped before they ever reach the queue. Works on direct enqueues and Topic publishes, with per-subscriber opt-out.

Send an idempotencyKey with a message and any repeat of that key within the TTL window (24 hours by default) is skipped, and reported back as deduplicated rather than as an error. On a Topic the key is passed to every subscriber, and each subscriber can turn deduplication off for its own queue.

Enqueue reference →
📦

Bulk Enqueue & Dequeue

Atomic operations for enqueuing and dequeuing many items at once, for best throughput.

Enqueue up to 1,000 messages in one request, and dequeue up to 100 at a time with the count header. Each call is a single actor turn and a single state-store transaction, so a batch either lands completely or not at all.

Enqueue reference →
⋮

Competing Consumers / Relaxed FIFO

Run many concurrent Dequeue operations in a traditional competing-consumer pattern.

By default, while any message on a queue is locked, further locked dequeues are refused, so one consumer at a time works through it in order. Set allow-competing-consumers and many consumers can each hold their own locks at once, trading strict ordering for throughput.

Locks and competing consumers →
❌

Dead-Lettering

Poison messages move to a dedicated dead-letter queue without blocking the main queue — on request, or automatically once they exceed the max delivery count.

Any locked message can be moved to {queue}-deadletter with one call. A message that is nacked or whose lock lapses too many times (10 by default) is moved there automatically. The dead-letter queue is an ordinary queue, so you inspect or reprocess it with the same API.

Dead Letter reference →
🌐

Built-in HTTP Sink

Forward messages to any webhook automatically — no custom control loop required.

Register a webhook URL against a queue and daprMQ delivers batches of messages to it. Reply 200 and the batch is acknowledged; reply 202 and you acknowledge each message yourself later; any failure leaves the messages to be redelivered when their locks lapse. You choose the concurrency (up to 100 in flight) and the lock TTL.

HTTP Sink reference →
↻

Streaming Consumers

Open one gRPC stream and the server pushes messages as your handlers free up, renewing locks for you — several times faster than polling.

A Consume stream keeps up to your prefetch count of messages in flight. The server renews their locks while they are being handled, refills as you settle them, and hands back anything unsettled the moment the stream closes. Every SDK wraps it in a QueueConsumer: your handler succeeds and the message is acknowledged, it throws and the message is nacked.

Consume stream reference →
📁

Optimised Memory Strategy

Queues split into fixed-size segments so memory and network usage stay bounded.

Each priority level is stored as a chain of 100-message segments. Enqueue writes to the tail segment and Dequeue reads from the head, and the segments in between stay in the state store until they are needed. A queue holding millions of messages costs about the same per operation as an empty one.

Segment offloading →
📎

Large Object Support

Enqueue oversized payloads to external object storage (S3, Azure Blob Storage) and dequeue lightweight claim tokens — queue state never carries the bytes.

Send the raw bytes of a file to enqueue-object and daprMQ streams them to object storage through a Dapr binding (S3, Azure Blob Storage, or a local volume). The queue carries only a small claim token, which consumers exchange for the object when they need it.

Large object reference →
💾

Persistent

Backed by any Dapr state store — PostgreSQL, Redis, Cosmos DB, and more.

Queues live in whichever Dapr state store you point daprMQ at, as long as it supports Dapr actors: PostgreSQL, Redis, Cosmos DB, MySQL, MongoDB and more. Every operation is one transaction against that store, so nothing is held only in memory.

How it works

Why the Dapr dependency?

Rather than reinvent proprietary infrastructure, daprMQ builds on Dapr's hardened, open-source building blocks:

  • Bring any Dapr-supported state store for queue persistence — Postgres, Redis, Cosmos DB, or any of Dapr's 20+ supported stores, with zero code changes.
  • Horizontal scaling for free — Dapr's actor runtime handles placement and re-activation across instances, so queues scale out without daprMQ writing its own sharding logic.
  • Strict FIFO without hand-rolled locks — each queue actor gets single-threaded, turn-based execution from Dapr, which is what guarantees ordering.
  • No broker cluster to run or patch — daprMQ runs anywhere Dapr runs: Kubernetes, a VM, or local Docker Compose.
  • High availability from the control plane — Dapr's placement service tracks actor health and re-activates queue actors elsewhere on instance failure, so daprMQ doesn't need to build its own failover logic.
  • Bounded memory, whatever the queue depth — every queue is split into 100-message segments. Only the head and tail segments of a queue are ever held in memory; every segment in between is unloaded, via Dapr's keyed state API. So memory and network usage scale with the work done, not with how many messages are sitting in the queue.
  • Unlimited queues, created on demand — every queue is just a Dapr actor, so there's nothing to provision upfront; spin up as many as you need and idle ones cost nothing until activated.
  • An idle queue costs nothing — a queue sitting untouched with millions of messages consumes zero memory; Dapr only activates and loads an actor when it's actually invoked. Idle queues are automatically unloaded from memory.

FAQ

Does my product have to use Dapr in any way to use daprMQ?

Absolutely not. Dapr is how daprMQ is built, not something your apps need to adopt. daprMQ runs as its own service, and your apps talk to it like they would talk to any other queue:

  • Plain HTTP and gRPC — daprMQ exposes a standard REST and gRPC API. Anything that can make a web request can enqueue and dequeue, even curl.
  • No sidecar next to your app — only the daprMQ server runs with a Dapr sidecar. Your producers and consumers don't need one, and don't need Dapr installed.
  • No Dapr SDK — the .NET, Java, Go, Python and TypeScript clients are thin HTTP/gRPC clients with no dependency on Dapr's libraries.
  • Run your apps anywhere — your apps can sit on Kubernetes, VMs, serverless functions, or a developer laptop, as long as they can reach the daprMQ endpoint.
  • Push delivery to any endpoint — the built-in HTTP Sink delivers messages to any HTTP URL, so a consumer can be an ordinary web service that never knows Dapr exists.
  • Already on Dapr? That works too — if your apps do run Dapr, nothing changes: they use the same HTTP/gRPC API and SDKs as everyone else.

Think of Dapr as daprMQ's storage and scaling engine. You run it once, alongside daprMQ, or let a managed service run it for you.
