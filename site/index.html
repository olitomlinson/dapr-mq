Features

Everything a modern transactional queue needs.

Just enqueue and dequeue is all you need to get started! Every other feature is optional, and layers on cleanly when you need it.

⇄

It Just Works

Enqueue and Dequeue — that's the whole API surface. Queues are created on-demand, no provisioning step.

📡

HTTP and gRPC API Surface

Call daprMQ over simple HTTP or gRPC interfaces

📜

Guaranteed FIFO

Strict first-in-first-out ordering per queue — no reordering, no surprises, no partitions to reason about.

⚡

Priority Support

Route urgent messages ahead of normal ones. Unbounded priority levels, 0 = highest.

✓

Acknowledgements

Optional at-least-once delivery — Ack, Nack, Extend Lock, or Ack up to 1000 at once. An unacknowledged message goes back to the position it was taken from, not the tail.

📡

Pub Sub

Publish messages to a Topic, automatic fan-out to many independent Subscriber Queues.

📊

Session / Message Group

Messages within a Queue can be assigned a Session ID. Consumers can lease one or more Sessions and receive a FIFO stream of messages

🔑

Message Deduplication

Attach a client-supplied Idempotency key to a message — duplicate submissions within a configurable TTL window are silently dropped before they ever reach the queue. Works on direct enqueues and Topic publishes, with per-subscriber opt-out.

📦

Bulk Enqueue & Dequeue

Atomic operations for enqueuing and dequeuing many items at once, for best throughput.

⋮

Competing Consumers / Relaxed FIFO

Run many concurrent Dequeue operations in a traditional competing-consumer pattern.

❌

Dead-Lettering

Poison messages move to a dedicated dead-letter queue without blocking the main queue — on request, or automatically once they exceed the max delivery count.

🌐

Built-in HTTP Sink

Forward messages to any webhook automatically — no custom control loop required.

↻

Streaming Consumers

Open one gRPC stream and the server pushes messages as your handlers free up, renewing locks for you — several times faster than polling.

📁

Optimised Memory Strategy

Queues split into fixed-size segments so memory and network usage stay bounded.

📎

Large Object Support

Enqueue oversized payloads to external object storage (S3, Azure Blob Storage) and dequeue lightweight claim tokens — queue state never carries the bytes.

💾

Persistent

Backed by any Dapr state store — PostgreSQL, Redis, Cosmos DB, and more.

⌹

Helm Deploy

Ship to Kubernetes with the published Helm chart — gateway and worker deployments, optional HPA, and a KEDA scaler that autoscales your consumers on queue depth.

How it works

Why the Dapr dependency?

Rather than reinvent proprietary infrastructure, daprMQ builds on Dapr's hardened, open-source building blocks:

  • Bring any Dapr-supported state store for queue persistence — Postgres, Redis, Cosmos DB, or any of Dapr's 20+ supported stores, with zero code changes.
  • Horizontal scaling for free — Dapr's actor runtime handles placement and re-activation across instances, so queues scale out without daprMQ writing its own sharding logic.
  • Strict FIFO without hand-rolled locks — each queue actor gets single-threaded, turn-based execution from Dapr, which is what guarantees ordering.
  • No broker cluster to run or patch — daprMQ runs anywhere Dapr runs: Kubernetes, a VM, or local Docker Compose.
  • High availability from the control plane — Dapr's placement service tracks actor health and re-activates queue actors elsewhere on instance failure, so daprMQ doesn't need to build its own failover logic.
  • Bounded memory, whatever the queue depth — every queue is split into 100-message segments. Only the head and tail segments of a queue are ever held in memory; every segment in between is unloaded, via Dapr's keyed state API. So memory and network usage scale with the work done, not with how many messages are sitting in the queue.
  • Unlimited queues, created on demand — every queue is just a Dapr actor, so there's nothing to provision upfront; spin up as many as you need and idle ones cost nothing until activated.
  • An idle queue costs nothing — a queue sitting untouched with millions of messages consumes zero memory; Dapr only activates and loads an actor when it's actually invoked. Idle queues are automatically unloaded from memory.

Get Started

Install in two steps

Install the server into a cluster running Dapr 1.18+ with a Dapr state store, then add an SDK. Everything is a pre-release until 1.0.

Server (Helm)
helm install daprmq oci://ghcr.io/olitomlinson/charts/daprmq \
  --devel -n daprmq \
  --set dapr.stateStoreName=statestore
SDK
dotnet add package DaprMQ.Client --prerelease
pip install daprmq-client
npm install @daprmq/client
go get github.com/olitomlinson/dapr-mq/sdks/go

Full install guide, including the state store, on GitHub.

API

HTTP & gRPC API Surface

If you do not wish to use an SDK, all of the capabilities are available via API

Enqueue
curl -X POST http://localhost:8002/queue/my-queue/enqueue \
  -H "Content-Type: application/json" \
  -d '{
    "items": [
      {
        "item": { "task": "first" },
        "priority": 1
      }
    ]
  }'
Dequeue
curl -X POST "http://localhost:8002/queue/my-queue/dequeue"
# {
#   "items": [
#     { "item": { "task": "first" }, "priority": 1 }
#   ]
# }
